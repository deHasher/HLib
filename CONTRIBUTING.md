# Участие в разработке HLib

## Документация

Редактируйте `docs/README.md` и страницы `docs/wiki/*.md`. Корневой `README.md` и GitHub Wiki — результаты генерации.

Для значения из `gradle.properties` используйте имя свойства в двойных фигурных скобках, например `{{lib_version_plugin}}`. Доступны все свойства файла: версии HLib, Java, API и зависимостей, имя библиотеки, адреса и другие параметры. Неизвестное имя останавливает генерацию до записи файлов.

После правок выполните:

```bash
python scripts/render-docs.py
python scripts/render-docs.py --check
```

Добавьте в commit исходники и обновлённый `README.md`. Страницы `build/wiki/` генерируются локально и в основной Git-репозиторий не добавляются.

Workflow `docs` проверяет pull request. При push в `master` он подставляет параметры, при необходимости коммитит README и публикует страницы в Wiki. Ручной повторный запуск доступен в GitHub Actions. Автоматический commit README не запускает новый workflow.

При смене версии достаточно изменить `lib_version_plugin` в `gradle.properties`. Также автоматически подставляются остальные использованные в шаблонах свойства. Поведение методов не выводится из кода автоматически: при изменении API обновите объяснение и примеры.

Для первоначальной настройки в репозитории должна быть включена Wiki и создана хотя бы одна страница. Используется встроенный `GITHUB_TOKEN` с разрешением `contents: write`. Не редактируйте управляемые страницы через редактор Wiki: следующая синхронизация заменит их содержимое. Посторонние страницы генератор не удаляет; удаление или переименование страницы в `docs/wiki` требует отдельно удалить старую страницу Wiki.

## Стиль Java

- Для изменяемых списков используйте `Lists.newArrayList(...)` из Guava вместо `new ArrayList<>(...)`. Неизменяемые списки создавайте через `List.of(...)`, `List.copyOf(...)` или `Stream.toList()`, когда это соответствует контракту.
- Для изменяемых карт используйте `new ConcurrentHashMap<>()` вместо `new HashMap<>()`, для множеств — `ConcurrentHashMap.newKeySet()` вместо `new HashSet<>()`. Это правило действует для новых и изменённых Java-классов целиком. Учитывайте запрет `null`; сохраняйте необходимые блокировки составных операций. Коллекции с необходимым порядком или сравнением по идентичности не заменяйте обычной конкурентной картой.
- Поля с Lombok-аксессорами называйте в `lowerCamelCase`: `modernBlockStateIdsMap` → `getModernBlockStateIdsMap()`, без имён вида `MODERN_BLOCK_STATE_IDS_MAP` и `getMODERN_BLOCK_STATE_IDS_MAP()`.
- Обход коллекций оформляйте через `.forEach(...)` вместо `for`. Если нужен ранний выход, используйте `anyMatch`, `allMatch`, `findFirst` или другую подходящую операцию stream с остановкой при получении результата; не имитируйте `break` через `AtomicBoolean` или исключения. Сохраняйте порядок, последовательное выполнение и прежние побочные эффекты.
- Вместо `String.join(...)` используйте `Tools.join(CharSequence delimiter, Object... elements)`. Метод преобразует элементы через `String.valueOf` и раскрывает переданную `Collection<?>` на один уровень. Произвольный `Iterable`, который не является `Collection`, сначала преобразуйте в коллекцию; массив примитивов также нельзя передавать как готовый список элементов.
- Для массивов объектов используйте `Stream.of(array)` вместо `Arrays.stream(array)`. `Stream.of(primitiveArray)` создаёт stream из одного массива: для `int[]`, `long[]` и `double[]` нужны `IntStream.of`, `LongStream.of` и `DoubleStream.of`; для других примитивных массивов используйте подходящий доступ по индексу через `IntStream.range`. Коллекции обходите через их `.stream()`.
- Простые DTO оформляйте как `record`, когда это сохраняет нужную семантику, ограничения API и производительность. Не превращайте в record объекты, которым нужны изменяемые поля, наследование, особая идентичность или закрытый конструктор публичного API. Компоненты record не делают вложенные коллекции неизменяемыми: при необходимости сохраняйте защитные копии.
- Для тривиальных геттеров и сеттеров используйте Lombok `@Getter` и `@Setter`, в том числе для статических полей. Статические поля аннотируйте явно: аннотации уровня класса их не охватывают. Сохраняйте доступность, для внутреннего состояния используйте `AccessLevel.PRIVATE`; у `final`-полей допускается только геттер. В коде обращайтесь к состоянию через эти методы, кроме инициализации полей. Не расширяйте публичный API и не раскрывайте внутренние mutable-объекты ради аннотации. Методы с валидацией, вычислениями, защитным копированием или побочными эффектами сохраняйте; у record используйте нативные методы компонентов.
- Для изменения регистра строк обязательно используйте `.toUpperCase()` и `.toLowerCase()` без аргументов. Передавать `Locale.ROOT` в `toUpperCase` или `toLowerCase` запрещено.
- Отладочные сообщения выводите только через `Tools.debug(player, message)`; для консоли передавайте `null` вместо игрока. Не используйте для отладки logger любого уровня, `System.out` или `System.err`.
- Обычные сообщения игроку или в консоль отправляйте только через `Informer.send(...)`: `Informer.send(player, message)` для адресата и `Informer.send(message)` для консоли. `Informer.component(...)` подготавливает компонент и не отправляет сообщение. Для специальных каналов сохраняйте соответствующие API title, action bar и boss bar.
- Применяйте эти правила к новым и текущим изменённым Java-файлам целиком. Остальной legacy-код не переписывайте попутно.

## Проверка кода

Используйте Gradle Wrapper и версии Java из `gradle.properties`. Для полного `build` необходимы JDK сборки и отдельный toolchain Checkstyle. На Windows:

```powershell
.\gradlew.bat clean build
```

На Linux и macOS:

```bash
./gradlew clean build
```

`build` запускает компиляцию, Checkstyle, SpotBugs и упаковку. CI релиза выполняет только `clean shadowJar`. Проверяйте изменённую интеграцию на целевой платформе: успешная компиляция не подтверждает совместимость с каждой версией Minecraft или стороннего плагина.
